# ESP8266 staging Wi-Fi build

For the practical delayed-display/manual-save workflow, use [the staging operator guide](../../docs/STAGING-SCALE-OPERATOR-WORKFLOW.md). It accepts explicitly reviewed UNVERIFIED estimates from usable observations up to five seconds old, while preserving the separate 500 ms verified preview gate. No new calibration session is required.

Open dloop_wifi_scale.ino with ESP8266 core 3.1.2 and select NodeMCU 1.0 (ESP-12E Module).

Required Tools > MMU setting: **16KB cache + 48KB IRAM and 2nd Heap (shared)**.

Compile-only equivalent:

```sh
arduino-cli compile --fqbn esp8266:esp8266:nodemcuv2:mmu=4816H firmware/dloop_wifi_scale
```

The staging TLS 1.2 endpoint was tested with verified CA/hostname and did not acknowledge a requested 4096-byte max_fragment_length extension. The current client therefore keeps a full 16384-byte TLS receive buffer plus core overhead; MFLN is optional. Core 3.1.2 prefers the enabled IRAM heap for these buffers. No insecure TLS mode or small-buffer fallback is used. The build intentionally fails without the required second heap rather than silently reverting to the known insufficient DRAM-only arrangement.

HTTPClient uses a cloned client sharing the TLS context. The checked clone preserves connect-time error diagnostics and returns success only after the core's authenticated hostname-based TLS connection succeeds. HTTP headers/bodies are sent afterward. CA trust anchors, SNTP/certificate time, token authentication, calibration and freshness gates are preserved.

Inspect iram_heap/iram_block plus tls_heap_before/tls_block_before and HTTP results in a separately approved device test. Compile success cannot establish dynamic allocation headroom or timing behavior after the cache/MMU change. No flash is authorized by these instructions.

wifi_private.h and compiled firmware contain credentials: keep them private. After USB source changes regenerate scale_core.generated.h with node scripts/sync-wifi-scale-core.mjs.

## Sampling, calibration and serial scheduling

Wi-Fi-only changes leave the radio-off USB preprocessed implementation unchanged. Sensor/EEPROM initialization completes before Wi-Fi startup. A queued startup line reports EEPROM availability, strict/approximate record validity, startup mode and factor-restored flags; no factors, passwords or tokens are printed. It never writes EEPROM or auto-selects approximate calibration.

At 115200 baud with Newline selected, send `DEBUG CALIBRATION` to request `#DEBUG WIFI_CALIBRATION eeprom_ready=... strict_valid=... approximate_valid=... active_mode=... factor_active=...` at any time, including during calibration. This Wi-Fi-only command reads the existing EEPROM emulation mirror into local copies without begin/put/commit or any calibration-state change. `factor_active` describes current RAM calibration availability; the one-time startup `factor_restored` flag describes startup restoration. No factors or offsets are printed. Validity is structural/checksum validity, not a claim of physical accuracy or an independent flash readback. Output uses the bounded serial queue and may be delayed or dropped under existing overflow handling; it cannot change thresholds, persist calibration or replay startup. The exact installed device build must be checked separately; local compilation does not install this command.

All Wi-Fi diagnostics use the existing line-atomic serial queues and shared formatter buffer. Wi-Fi UART draining uses availableForWrite with at most 256 bytes and a 500-microsecond loop budget, without waiting for UART space. Overflow reporting stays fail-closed; serial_protocol_lost, serial_diagnostic_lost and serial_format_lost distinguish the sources. No buffer capacities or stability thresholds were changed.

Synchronous network work is deferred during strict calibration attempts (including an unstable ZERO), pending approximate calibration, full trace capture, pending overflow END and queued serial backlog. Strict/approximate successful acceptance or explicit cancellation/mode selection releases the calibration pause; an unsuccessful calibration remains paused for operator resolution. Summary/ordinary monitoring does not itself request a calibration pause.

Calibrated uploads retain one attempt per second after completion. Uncalibrated preview uploads use a 250 ms pause after completion (at most four attempts/second), with a two-second failure pause. Latest-only frames retain the 500 ms expiry; sampling target stays 100 ms. Network block duration/max and net_paused are bounded queued diagnostics. Lower upload cadence can make the UI stale between packets because the 500 ms freshness rule is deliberately unchanged. HTTPS remains synchronous during ordinary uploads and can still introduce sampling gaps; no continuous hard-real-time guarantee is claimed. Hardware timing, heap and real staging upload behavior remain unverified without a separately approved flash/test.

## HTTP 422 diagnostics

The queued `WIFI_HTTP` line reports `frame_queue_ms` (frame creation/queue to upload start), `tls_connect_ms` (the preceding connection warmup, including DNS/TCP, TLS handshake and certificate validation), `http_response_ms` (this frame's request-send/response-header time), `response_read_ms` (bounded response drain) and `frame_response_ms` (frame queue to response headers). TLS warmup now occurs before this frame exists, so its duration is not part of `frame_response_ms`. These are device monotonic durations, not clock offsets or a measurement of server processing alone. The existing diagnostic rate limit still applies.

Successful and HTTP 422 responses are drained using the completed request buffer with a 512-byte cap and bounded read timeout. Only HTTP 422 responses are parsed for error codes. The parser accepts the API's flat string-valued JSON envelope and emits only literal `api_error=invalid_frame`, `api_error=invalid_preview`, or `api_error=stale_upload`. Other, malformed, incomplete, duplicate-code or oversized responses produce no API error label. Response text, headers and request contents are never logged. Timestamp generation, queue expiry, server freshness rules, authentication and TLS verification are unchanged. Compile-only parser cases run with `node scripts/check-wifi-http-diagnostics.mjs`; no device or server connection is made.

The capture sink explicitly advertises remaining writable capacity and marks full/expired capacity as terminal. ESP8266 core 3.1.2's BearSSL peek-buffer transfer otherwise sees the inherited `Print` capacity of zero and waits until timeout without delivering response bytes to the parser. Regression checks cover capacity boundaries and the installed core transfer path. The API emits `application/json; charset=utf-8`; this parser reads decoded HTTP body bytes without depending on content-type header collection. Hosted response format and the exact rejection still require an actual allowlisted device result.

## Fresh frames after TLS warmup

`sentAtMs` remains the UTC frame-creation/queue time, not a post-handshake replacement timestamp. The backend uses receipt minus this timestamp to age `live.ageMs`, which independently represents sensor age at frame creation. A long handshake must not be hidden by retimestamping the same measurement.

When disconnected, the transport clears the old queued frame, establishes verified hostname-based TLS, then returns to the acquisition loop without sending application headers or data. A later tick may upload a new frame only within the existing 500 ms queue limit. HTTPClient's clone shares the verified TLS context and is prohibited from reconnecting during POST; a lost connection fails closed and requires another warmup followed by another fresh frame. A completely drained successful response may retain the already verified connection when the server permits HTTP keep-alive. Incomplete/oversized responses, errors and server closes require a new verified warmup and fresh frame; TLS session resumption state is retained. Status/fault frames may still report missing samples, with stale preview values cleared by the existing core rules. Server 5-second upload and 1-second future-clock limits are unchanged.

Run `node scripts/check-wifi-tls-freshness.mjs` for lifecycle source guards and offline execution of the real PHP API validation against a PDO test double. It tests >5-second handshake-old-frame rejection, fresh post-handshake frames, stale previews, clock skew and exact window boundaries without connecting to any database. Hardware scheduling and network behavior still require separately approved flashing/testing.

## SINGLE_POINT reference-based calibration (Wi-Fi build only)

This mode fits an empty-platform offset and a factor from one independently measured object. It checks repeated removal/replacement, **not independent accuracy, linearity or uncertainty**. The reference machine's error transfers to the result. Firmware still limits measurements/references to 5000 g despite the 20 kg load-cell rating. No guaranteed accuracy is reported.

At 115200 baud with Newline, the future operator procedure for the known 1802 g object is:

1. Empty the platform; send `SINGLE CAL BEGIN`. This clears active RAM calibration and pauses HTTPS, but does not overwrite any saved record. Wait for `BASELINE_READY`.
2. Place the actual 1802 g object, then send `SINGLE CAL LOAD 1802`. Wait for `NEED_EMPTY`. The factor is now frozen.
3. Remove the object, send `SINGLE CAL EMPTY`, and wait for `NEED_REFERENCE`.
4. Replace the same object, send `SINGLE CAL CHECK 1802`, and wait for the next state. Repeat steps 3–4 for **three** cycles. Do not substitute an invented mass or skip removal.
5. At `READY_TO_ACCEPT`, leave the reference untouched until the final live filter qualifies (normally about 8 seconds with quiet 100 ms samples), then explicitly send `SINGLE CAL ACCEPT`. It must report `ACCEPTED persisted=1`; otherwise inspect `SINGLE CAL STATUS` and stop on failure. An early ACCEPT does not save or bypass qualification.
6. Remove the object and inspect local `#DEBUG SINGLE_POINT` values after settling. Reload it to check repeatability only. `SINGLE CAL STATUS` and `DEBUG CALIBRATION` do not write EEPROM. `SINGLE CAL ABORT` discards the pending RAM attempt and returns to STRICT; it does not erase saved records. `MODE STRICT` or `MODE APPROX` exits this mode using the existing saved workflows.

Each empty/loaded stage waits 5 seconds and then requires 200 consecutive samples spanning at least 19 seconds, with 75–150 ms intervals, 500 ms freshness and a 120-second per-stage timeout. The initial baseline/reference must have an unambiguous response and plausible finite factor. Noise/drift/outlier gates use the existing APPROX quality limits: 25 g total range, 6 g central range, 1.5 g MAD, 2 g half-shift, 0.25 g/s slope, 5 g block span and 8 g maximum deviation/jump. Empty returns must be within 5 g of zero with no more than 3 g inter-cycle spread. Loaded repeats must stay within 20 g of the declared reference and span no more than 20 g across cycles; these are rejection thresholds, not accuracy claims. Acquisition/serial losses fail the attempt. Failed attempts cannot be accepted.

The separate 48-byte version-1 record occupies EEPROM bytes **80–127**, following STRICT 0–19 and APPROX 32–79 within the unchanged 128-byte allocation. It stores its own magic, profile, reference mass, frozen factor, offset, three-cycle results and checksum. Only successful explicit ACCEPT writes it. Earlier saved records remain intact, including the previous SINGLE_POINT record on BEGIN/ABORT. Boot reads the record but defaults to STRICT; explicitly send `MODE SINGLE_POINT` after reboot to restore a valid SINGLE_POINT record and inspect labelled readings. Structural validity does not establish physical accuracy.

SINGLE_POINT reuses the inactive APPROX collector's raw/timestamp/scratch buffers; the workflows are mutually exclusive. It does not change the USB build. HTTPS is paused throughout SINGLE_POINT mode, including after acceptance: **the existing API/dashboard do not support this provenance**. Values appear only as `#DEBUG SINGLE_POINT mode=SINGLE_POINT reference_based=1 independent_accuracy_verified=0 calibrated=... stable=... gross_g=...`. Pending/unqualified/stale readings report `gross_g=null`. These lines are monitor diagnostics, never v1 STRICT/APPROXIMATE measurements or inventory inputs. The staging dashboard becomes stale/offline rather than receiving mislabelled measurements; remote SINGLE_POINT support requires a separate reviewed API/UI change and deployment. No such change is bundled here.

Run `node scripts/check-single-point-calibration.mjs` plus the existing calibration/protocol/transport regressions. Numerical/state/persistence assertions also compile with the NodeMCU build. These are synthetic tests; actual load behavior, EEPROM flash endurance/readback, timing and heap margins require separately approved hardware testing. Do not flash or begin calibration as part of local verification.

### SINGLE_POINT acquisition-gap evidence

On `ACQUISITION_GAP`, one bounded queued `#DEBUG SINGLE_CAL` line preserves `idGap`, `tooFast`, `tooSlow`, exact `prevId`/`currentId`, `prevMs`/`currentMs`, `deltaMs`, `samplesBeforeClear` and `phase`. It also includes the poll interval/read duration, prior poll readiness and the count/time of HX711-not-ready polls between accepted conversions. `condition` gives a primary cause; inspect all three flags because multiple conditions can occur together. `SINGLE CAL STATUS` reprints the latched evidence without restarting calibration, writing EEPROM or changing the factor. The existing queue overflow rules still apply. No raw measurements, credentials or request contents are added to these diagnostics.

The existing rejection rule remains unchanged: while collecting (including the initial settling period) and during final live qualification, each accepted acquisition ID must advance by one and the conversion-completion timestamps must differ by 75–150 ms inclusive. The first sample after BEGIN or a new collection establishes the phase-local anchor; it is not compared with an old ID. Freshness remains 500 ms and the phase timeout remains 120 seconds. `fail()` clears the sample count, so the older summary `samples=0/200` does not establish that no samples were acquired.

Interpret a 200 ms gap with a preceding not-ready poll as a missed conversion/readiness opportunity; a large `pollDeltaMs` suggests delayed main-loop scheduling instead. Neither alone proves a hardware fault. HTTPS is deferred while SINGLE_POINT mode is active, but SDK background Wi-Fi, UART activity, diagnostic CPU work and a not-ready HX711 can still affect scheduling. The original scheduler waited 100 ms between all polls, so one not-ready poll deferred the next opportunity by a whole sample period. The SINGLE_POINT-only readiness retry fix below removes that quantization without changing the acceptance rules. Run `node scripts/check-single-point-gap-diagnostic.mjs` and the numerical calibration tests; capturing new hardware evidence requires a separately approved firmware installation and test.

### SINGLE_POINT readiness retry scheduling

SINGLE_POINT keeps a 100 ms target measured from the last genuine HX711 read. Once due, a not-ready result is retried every 5 ms without busy waiting. Each loop checks readiness at most once; data and acquisition IDs advance only after a real ready/read. A read never occurs before the 100 ms target. STRICT, APPROX and USB continue using their original 100 ms polling schedule. The 75–150 ms consecutive-sample gate, 500 ms freshness, all quality checks and EEPROM layouts are unchanged.

For example, a conversion becoming ready at 101 ms previously missed the 100 ms poll and was read at 200 ms. It is now eligible at 105 ms. The simulated old ready/not-ready/ready sequence reproduces the observed consecutive IDs and 200 ms gap. A genuinely 160 ms conversion still fails, as it must; no samples are synthesized or stale values reused. Main-loop stalls can still miss deadlines.

The installed HX711 library configures channel A/gain 128 through D5/D6; it does not control or read the HX711 RATE pin. The manufacturer's datasheet specifies nominal 10 SPS with RATE low and 80 SPS with RATE high. The actual module wiring, oscillator rate and maximum conversion time cannot be established from firmware or the one 200 ms observation. No RATE wiring, gain, sample clock or thresholds are changed. If actual conversion availability or scheduling delays cannot meet 150 ms, calibration must remain rejected pending hardware/timing investigation. Test with `node scripts/check-single-point-acquisition.mjs`; hardware confirmation needs separate approval.

### SINGLE_POINT stage deadlines and command results

Every transition starts its own unchanged 120-second deadline. In particular, `BASELINE_READY` starts a fresh **operator-wait** deadline when the baseline completes. A valid `SINGLE CAL LOAD 1802` before expiry enters `REFERENCE` and starts a new collection deadline. Each EMPTY/CHECK transition and final `READY_TO_ACCEPT` transition likewise resets the stage start. Deadline validation occurs before a LOAD can start a new stage; an expired or already-failed attempt cannot be revived by LOAD. Exactly 120000 ms is allowed; elapsed time greater than 120000 ms fails. Sample freshness (500 ms) is checked first. Normal loaded collection needs about 25–35 seconds with valid samples, including the 5-second settle, rather than the whole 120-second allowance.

The only `STEP_TIMEOUT` producer is `Session::tick()`, reached from accepted-sample processing, the regular main-loop check and command handling. Operator-wait samples continue refreshing `lastMs` while the stage deadline remains fixed. The old summary cleared counts on failure and could not distinguish an operator-wait timeout from a collection timeout.

New bounded diagnostics retain `#DEBUG SINGLE_TIMEOUT previous_state=... timeout_stage=... stage_start_ms=... at_ms=... elapsed_ms=... limit_ms=120000 deadline_ms=... samples_before_failure=... cycles_before_failure=...`. Times are unsigned device milliseconds, including wraparound, not UTC. `previous_state` is the state preceding entry to the timed-out stage. Fixed-label `#DEBUG SINGLE_COMMAND command=LOAD accepted=1 previous_state=BASELINE_READY result_state=REFERENCE ...` confirms command acceptance and deadline reset, not completion of any samples. `accepted=0 result_state=FAILED` with `timeout_stage=BASELINE_READY` identifies an expired operator wait. A REFERENCE timeout with a nonzero pre-failure sample count proves loaded collection had begun. During the initial settling period a valid REFERENCE stage can still have zero retained samples.

`SINGLE CAL STATUS` replays latched timeout and latest command evidence without ticking, extending the deadline, restarting calibration or writing EEPROM. BEGIN/ABORT clear the session's evidence. No command arguments, secrets or raw measurements are added to these diagnostics. Run `node scripts/check-single-point-timeout-diagnostic.mjs` for compiled state/boundary tests and format/integration checks. Existing summary-only hardware evidence cannot retrospectively establish LOAD acceptance or the timed-out stage; capturing these new diagnostics requires separately approved installation and testing. No timeout or acceptance rule is relaxed.


## Staging UNVERIFIED Wi-Fi live preview (no new calibration)

The shared USB measurement core remains unchanged for uncalibrated frames: `grossG=null`, `stable=false`, `calibrated=false`, `fault=CALIBRATION_REQUIRED`, and `live.grams=null`. Fresh `live.raw` counts are transported through the existing authenticated API. The browser alone computes `(filtered raw - explicitly selected browser display tare) / 213.656` after the existing operator acknowledgement. The factor is never installed into device calibration or EEPROM. The UI says **UNVERIFIED ESTIMATE**, does not claim calibrated/stable measurement status, and never saves or deducts inventory automatically. Optional manual estimate saving remains a separate existing review/confirmation flow.

Normal telemetry must be explicitly selected in RAM if the device is in failed SINGLE_POINT mode. After separately approved installation of this build, use 115200 baud and Newline:

1. Send `DEBUG CALIBRATION` and `SINGLE CAL STATUS`; record only status flags. Do not send ZERO, CAL, BEGIN, ACCEPT or CANCEL.
2. Send `MODE STRICT`. This aborts the SINGLE_POINT session in RAM, clears queued telemetry, and selects the existing STRICT path. It does not put/commit/erase EEPROM. With the confirmed invalid STRICT record it remains uncalibrated. Send `DEBUG CALIBRATION` again: expect STRICT, the same validity flags and `factor_active=0`.
3. Confirm subsequent v1 frames have `calibrated=false`, `stable=false`, `grossG=null`, `live.grams=null`, and fresh numeric `live.raw`. Do not accept any estimate as calibration.
4. Confirm staging HTTP 200. `WIFI_HTTP response_complete=1` indicates bounded response completion; `tls_reuse_count` should grow without a handshake per request if the server permits reuse. `tls_connect_count` counts warmup attempts. A server close is honored, never bypassed. No response bodies, credentials or headers are logged.
5. Sign in to staging, choose Wi-Fi Scale, empty the platform and wait for fresh counts. Check the display-tare confirmation and click **Tare preview display**, then acknowledge the empty-platform baseline to enable the estimate. This is browser-only; do not use firmware ZERO EMPTY or change spool tare.
6. Place the known 1802 g object and check the estimated display against that reference. This tests the existing estimate; it is not independent calibration or an accuracy guarantee. Remove it and check the displayed zero. Confirm no automatic inventory change.
7. Test stale/offline behavior: samples older than 500 ms must disappear, not remain frozen as fresh. For Wi-Fi only, confirmation stays tied to the same browser baseline during brief stale intervals so new fresh packets resume the estimate automatically. No stale value becomes usable. Confirm acknowledgement resets after reconnect, calibration changes or a changed tare; USB acknowledgement behavior is unchanged. No hardware/network test is performed by local builds.

Keep-alive uses the installed core's server close policy and a fully consumed bounded response. If response draining fails, the connection is closed. If a socket dies before POST, the established-only client cannot silently re-handshake around an old sample. Every new TLS handshake returns to acquisition before selecting a fresh frame. The existing CA/hostname/time checks, bearer authentication, capture timestamps, 500 ms preview limit and 5-second API upload window are unchanged. Response and browser polling latency still count against freshness: this is best-effort live refresh, not a guarantee of an uninterrupted display on a slow shared host. Hardware verification must establish useful refresh latency; otherwise investigate latency instead of weakening freshness.

There are no backend implementation or database changes. Browser label changes require a separately approved staging frontend upload to appear on hosting. This workflow does not enable remote calibration. To stop preview, disconnect the scale or close the page; all calibration records remain intact. Restore the previous local firmware/frontend files if rollback is required; any flashing/upload requires separate approval. Do not generate a calibration, overwrite records, deploy production or change credentials as part of this checklist.

### Fresh sample demand and post-network filter recovery

An observed GET with `live.ageMs=850` and `reading.ageMs=257` establishes that the API calculated 593 ms of age before storage waiting, then cleared raw because the total exceeds 500 ms. It does not reveal whether the stored raw was originally numeric, or how much of 593 ms was sensor age, delivery delay or clock difference. The API's existing age calculation and expiry remain unchanged.

The transport now checks **sample age plus queue residence**, not queue residence alone. Once a routine numeric uncalibrated preview upload becomes due on an established TLS connection, it discards the older queued frame, requests a new acquisition, and returns to the main loop. The next actual sample can trigger frame construction without waiting for the next 250 ms periodic emit. Only one requested frame is queued; subsequent loops drain the serial writer instead of repeatedly emitting the same sample. Timestamps remain the actual frame timestamps, never replaced at transmission.

If blocking networking or a sensor fault invalidates the preview filter, pending numeric previews are dropped. Routine `CALIBRATION_REQUIRED` frames whose filter is still warming are not POSTed: sampling first rebuilds the unchanged five-sample filter. This prevents repeated long requests from continually resetting the filter before it can fill. Explicit sensor-fault null frames remain eligible, and no last-good numeric raw is substituted for an invalid filter. STRICT/APPROX/SINGLE_POINT algorithms, EEPROM and USB acquisition are unchanged.

The bounded queued `#DEBUG WIFI_SAMPLE` line reports `sample_age_frame_ms`, `sample_age_upload_ms`, `sample_age_complete_ms`, `waiting_fresh` and `warming`. These ages refer to the uploaded frame's latest sensor read, not HTTP latency alone; UINT32_MAX means unavailable/saturated. A completion age over 500 ms is reported truthfully and does not authorize stale display. The API and browser still count transport/polling age. Clock skew or irreducible hosting latency can still prevent usable previews.

After separately approved installation, verify at 115200 baud/Newline:

1. Send `MODE STRICT`, then `DEBUG CALIBRATION`; with the confirmed invalid record expect STRICT and `factor_active=0`. Do not send ZERO/CAL/BEGIN/ACCEPT or change records.
2. Observe genuine numeric `live.raw` after filter refill, while `calibrated=false`, `stable=false` and `live.grams=null`. Observe warmup nulls after long blocking gaps; they must not become fabricated numbers.
3. Match device frame sequence with the staging GET `/api/v1/scale-reading` and record only sequence, raw, sample age, storage age and receipt timestamp. Collect `WIFI_SAMPLE` plus existing queue/HTTP timing and reuse counters; never copy request bodies or authentication headers.
4. Check sample age at upload start is low after the fresh-read demand. GET age must remain at most 500 ms for a visible preview; otherwise retain stale display and investigate clock/delivery/GET latency. Compare `live.ageMs - reading.ageMs` with device creation/start ages to narrow the remaining delay.
5. On staging, empty-platform browser display tare and acknowledgement should enable the existing UNVERIFIED estimate. Check removal/replacement of 1802 g and stale/reconnect behavior without saving inventory. No calibration status is upgraded.

### Staging GET timing and conservative browser age

A captured GET with numeric raw, `live.ageMs=499`, `reading.ageMs=80` and a 1783 ms browser request was rejected by the previous conservative browser mapping as 2282 ms old. The 499 ms already contains device sample age, absolute POST receipt/capture clock difference and the 80 ms storage wait; the earlier portion is 419 ms, not a separately measured device-only age. No clock-skew allowance is removed or calibrated flag upgraded.

The authenticated staging scale GET can now return only nonsecret duration metadata in optional `timing`: `version=1`, `preSnapshotMs`, `authMs`, `lookupMs`. `preSnapshotMs` is rounded-down monotonic server time from API construction to **before** the age snapshot; it covers session/authentication and data lookup already preceding that snapshot. `authMs` includes session startup/possible lock wait plus administrator lookup; it is not pure CPU time. `lookupMs` covers the availability and live-reading queries. Request queuing/bootstrap before API construction, network travel, response serialization, browser parsing and main-thread scheduling remain in the residual duration and cannot be individually identified from these fields alone.

Timing and early session-lock release are gated to the exact staging database identity `dltsin_fila_stage`, origin list containing only `https://staging-fila.dlts.in`, and request host `staging-fila.dlts.in`. After the existing administrator authentication, the staging read-only scale route closes its session before querying live data; authentication, rotation and last-seen updates have already completed. No later session writes occur on that route. Production receives no timing metadata or changed session-close behavior.

The browser uses monotonic GET elapsed time. With valid version-1 timing, its remaining response-age allowance is `ceil(GET elapsed) - max(0, preSnapshotMs - 1)`. This removes only proven pre-snapshot server duration and keeps a 1 ms rounding margin. It does not halve RTT, remove all transport age or compare browser/server UTC clocks. Missing, malformed, impossible or out-of-range timing falls back to full RTT. Repeated sequences retain their original mapping and cannot become fresh through re-polling. The 500 ms limit remains unchanged: 499 ms plus an 84 ms allowance is still stale; a 100 ms snapshot plus that same 84 ms allowance is eligible.

Polling remains single-flight. For staging timing responses, the next delay is `max(0, 250 ms - completed request duration)` rather than adding another 250 ms after every request. There is never an overlapping periodic request. Untimed responses retain the existing completion-plus-250-ms cadence. This improves cadence but does not overcome irreducible network latency or a snapshot already at its freshness limit.
